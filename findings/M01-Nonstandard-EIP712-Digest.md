# M-01 | Non-Compliant EIP-712 Digest Calculation in deployProxyAndDistributeBySignature()

**Project:** Sparkn  
**Severity:** Medium 
**Vulnerability Category:** EIP-712 Non-Compliance / Signature Compatibility  
**Affected Contract:** `src/ProxyFactory.sol`  
**Affected Function:** `deployProxyAndDistributeBySignature()`  
**Test File:** `test/M01EIP712Digest.t.sol`  
**Testing Framework:** Foundry  


## 1. Summary

Sparkn uses EIP-712 domain separation to verify signatures authorizing contest reward distributions.

However, `ProxyFactory.deployProxyAndDistributeBySignature()` computes the message digest using `keccak256(abi.encode(contestId, data))` as the structured data hash.

This implementation omits the EIP-712 `typeHash` and does not hash the dynamic `bytes data` field according to the EIP-712 structured-data encoding specification.

Consequently, the digest produced by Sparkn differs from the digest generated by a standards-compliant EIP-712 implementation using the corresponding typed message schema.

This creates a signature compatibility issue. A signature produced by a standard EIP-712 signing client may be rejected by the on-chain Factory even when it was generated using the intended Organizer's private key.

The local Foundry PoC confirms that the two digest calculations differ and that the original Factory rejects a signature generated from the standard structured-data digest.

## 2. Root Cause

The affected function computes and verifies signatures as follows:

```solidity
bytes32 digest = _hashTypedDataV4(
    keccak256(abi.encode(contestId, data))
);

if (ECDSA.recover(digest, signature) != organizer)
    revert ProxyFactory__InvalidSignature();
```

OpenZeppelin's `_hashTypedDataV4()` combines the EIP-712 domain separator with a supplied structured-data hash.

It does not automatically construct the message-specific `typeHash` or encode dynamic message fields.

For example, consider the following typed structure:

```solidity
Distribute(bytes32 contestId,bytes data)
```

The corresponding EIP-712 structure hash should be calculated using:

```solidity
bytes32 typeHash = keccak256(
    "Distribute(bytes32 contestId,bytes data)"
);

bytes32 structHash = keccak256(
    abi.encode(
        typeHash,
        contestId,
        keccak256(data)
    )
);
```

The original implementation deviates from this construction in two ways.

**Missing type hash**

The original message hash does not commit to the declared EIP-712 structure type.

**Incorrect dynamic-field encoding**

The dynamic `bytes data` field is included through ordinary ABI encoding rather than being represented by `keccak256(data)`.

As a result:

```text
Original Sparkn structHash
!=
Standard EIP-712 structHash
```

And therefore:

```text
Original Sparkn digest
!=
Standard EIP-712 digest
```

**The root cause is an incomplete implementation of EIP-712 structured-data hashing despite using the standard domain-separated digest helper.**

## 3. Impact

### 3.1 Signature Verification Incompatibility

Signatures generated with a standards-compliant EIP-712 typed-data client may not match the digest reconstructed by the original Factory.

When the recovered signer does not equal the expected Organizer, the contract reverts with:

```solidity
ProxyFactory__InvalidSignature();
```

This behavior was reproduced in the local PoC.

### 3.2 Wallet and Frontend Integration Risk

Wallets and applications that use standard EIP-712 typed-data signing may produce signatures incompatible with Sparkn's custom digest calculation.

Integrations must reproduce the protocol's non-standard hashing behavior instead of relying on the expected typed-data encoding process.

This introduces unnecessary complexity and may cause otherwise legitimate distribution authorization attempts to fail.

### 3.3 Incomplete Typed-Message Binding

Omitting the `typeHash` means that the signed message does not follow the complete structure-aware encoding required by EIP-712.

This reduces interoperability with standard signing tools and makes the authorization scheme more difficult to independently validate.

### 3.4 Scope of Demonstrated Impact

The PoC demonstrates digest incompatibility and rejection of a standards-compliant typed-data signature.

It does not demonstrate:

- Signature forgery.
- Unauthorized transfer of contest rewards.
- Successful cross-contest signature replay.
- Direct financial loss.
- Exploitation on a deployed production contract.

Missing implementation binding, nonce handling, and deadlines are separate concerns that require independent analysis.

### 4.6 Test Results and Analysis

**Verified findings:**

1. Sparkn's original structure hash differs from the EIP-712 structure hash constructed using the selected schema.
2. The corresponding final message digests are different.
3. Signature recovery depends on the exact digest that was signed.
4. The original Factory rejects a signature derived from the standard structured-data digest.
5. Both local Foundry tests passed.

**Testing limitations:**

2. No browser-wallet or external `eth_signTypedData_v4` integration was tested.

4. The PoC does not establish a direct asset-theft scenario.
5. No patched implementation or regression test was executed.

The evidence therefore establishes a reproducible EIP-712 compatibility issue, rather than an independently demonstrated financial exploit.

## 5. Recommendation

Implement message-specific structured-data hashing according to the EIP-712 specification.

Define an explicit typed-message schema and corresponding type hash:

```solidity
bytes32 constant DISTRIBUTE_TYPEHASH =
    keccak256(
        "Distribute(bytes32 contestId,bytes data)"
    );
```

Compute the structure hash using the correct field encodings:

```solidity
bytes32 structHash = keccak256(
    abi.encode(
        DISTRIBUTE_TYPEHASH,
        contestId,
        keccak256(data)
    )
);
```

Then calculate the domain-separated digest:

```solidity
bytes32 digest = _hashTypedDataV4(structHash);
```

Additional recommendations:

1. Ensure that the frontend and on-chain contract use identical EIP-712 type declarations, field ordering, and domain values.
2. Add cross-implementation tests using standard EIP-712 signing clients.
3. Evaluate implementation binding, nonces, and deadlines separately as part of the broader signature authorization design.
4. Introduce a compatibility and migration strategy if existing signatures depend on the original hashing algorithm.

**Expected behavior after remediation:**

An Organizer signature generated using the protocol's published EIP-712 schema should recover the correct signer on-chain and proceed to subsequent business validations.

## 7. Conclusion

Sparkn's `deployProxyAndDistributeBySignature()` uses EIP-712 domain separation but does not construct its message-specific structure hash according to the EIP-712 specification.

The implementation omits the `typeHash` and fails to apply the required hashing procedure to the dynamic `bytes data` field.

The local Foundry PoC demonstrates that the original and standard digests differ and that a signature based on the selected standards-compliant typed-data schema is rejected by the original Factory.

**Test results: 2 passed, 0 failed.**

The reproduced finding establishes the historical EIP-712 encoding compatibility issue. The demonstrated scope is limited to digest construction and signature validation behavior.
